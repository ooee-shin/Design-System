# AX 전환 단계와 검증 계획

최종 목표는 요구사항에서 화면과 코드가 이어서 만들어지는 개발 환경이다. UI 시스템은 그 기반이며 목표 자체가 아니다.

## 5단계

| 단계 | 내용 | 1차 범위 |
| --- | --- | --- |
| 1 | UI 패키지 + Studio + 디자인 토큰 구축. 처음 계획의 Figma 디자인 시스템과 스토리북은 뺐다(`2026-09-18`·`2026-09-22`) | 포함 |
| 2 | Figma MCP 연동 — `2026-09-22` 에 요청 처리에서 Figma 를 빼며 걷어냈다. 이 저장소는 MCP 서버를 두지 않는다 | 제외 |
| 3 | 컴포넌트를 참고하는 채널 — Studio와 `llms.txt`. 처음 계획의 스토리북 MCP 는 두지 않기로 했다(`2026-09-18`) | 포함 |
| 4 | 에이전트 설정·룰 | 제외 |
| 5 | 요구사항 → 화면 생성 → 코드 → 스토리 → PR/배포 자동화 | 제외 |

3단계까지는 안전하게 도달 가능하다고 보며, 이후는 테스트 소요 시간이 변수다.

## 컴포넌트를 참고하는 채널

기획자와 다른 개발자가 컴포넌트를 바로 참고하는 표준 채널은 `apps/studio`다. 스토리북은 두지 않기로 했다(`2026-09-18`, [ai-environment.md](ai-environment.md)). Studio는 전달 범위에 포함하며, AI 가 읽는 색인은 저장소 루트의 `llms.txt`다.

`llms.txt`는 최우선 순위가 아니다. 다만 `docs/system/`을 단일 파일로 뽑아낼 수 있는 구조로 유지해 필요할 때 비용 없이 만들 수 있게 둔다.

## A/B 비교 검증

Figma에 들일 공수가 값어치를 하는지 판단하기 위한 품질 비교 테스트다.

| 안 | 방식 |
| --- | --- |
| A | Figma MCP를 경유해 코드 생성 |
| B | 컴포넌트만 주고 바로 코드 생성 |

**현재까지의 경험은 B안이 낫다.** Figma MCP를 물리면 오히려 디자인 시스템 코드를 잘 따르지 않았고, UI 키트만 보게 하는 쪽 결과가 좋았다.

### 2026-09-16 비교 결과

화면 둘(관리자 로그인, STO 지원요청)을 두 안으로 각각 만들어 쟀다. 두 안 모두 `/generate-code`와 `/review-design`을 같은 Skill로 돌렸고 모델은 Sonnet(`claude-sonnet-5`)이다. A안은 화면 설명 대신 Figma에서 다시 읽은 결과(레이어 이름·변수 이름·크기)와 [figma-component-map.md](figma-component-map.md)를 주었다. 자세한 절차와 한계는 [ai-environment.md](ai-environment.md)의 결과 절에 있다.

| 재는 것 | B안(컴포넌트만) | A안(Figma 경유) |
| --- | --- | --- |
| `/review-design` 위반 | 1건 (관리자 로그인) + 0건 (STO) | 0건 + 0건 |
| `@ooee/ui` 재사용 | 4/5, 16/16 | 4/5, 16/16 |
| 요청과 어긋난 자리 | 0건 + 1건 | 4건 + 5건 |

**위반 수와 재사용 비율로는 두 안이 갈리지 않는다.** 둘 다 같은 Skill과 같은 문서를 쓰므로 토큰·컴포넌트 규칙은 똑같이 지킨다. 갈리는 것은 **요청의 뜻이 남는가**다.

- A안은 화면의 동작과 미정 사항을 알 수 없다. Figma에는 「제출을 눌러야 반영된다」, 「이 값은 정하지 않았다」, 「이 링크는 목적지가 미정이다」가 없다. 그래서 A안의 STO 화면은 Figma의 `switch` 레이어를 보고도 Checkbox로 바꿀 근거를 찾지 못했고, 반대로 B안은 요청의 낱말과 `switch.md`를 견줘 바꾼 뒤 그 판단을 보고에 적었다.
- A안은 문구와 크기를 Figma 값으로 되돌리려다 시스템 규칙과 부딪친다. placeholder 문구, 아이콘 버튼 크기, 글자 색 위계에서 코드 쪽 규칙을 따르고 Figma와 달라진 자리가 화면당 4~5곳이었다.
- B안은 요청 문단이 머리말 주석으로 남아 다음 사람이 무엇이 정해졌고 무엇이 비었는지 읽을 수 있다. A안에는 그 문단이 없다.

**결론(`2026-09-16`, `2026-09-22` 에 폐기): Figma는 원본이 아니라 검토용 캔버스로 쓴다.** — 이 결론은 `2026-09-22` 에 Figma 를 요청 처리에서 아예 빼면서 지난 기록이 됐다. 지금은 sandbox 에서 띄워 보고 검사한다([ai-environment.md](ai-environment.md) 「2026-09-22 Figma 를 뺐다」). 아래는 그때의 기록이다. 코드로 먼저 만들고(`/generate-code`), Figma로 옮겨 사람이 보고(`/design-page`), 고친 것만 다시 읽어 코드로 되돌린다(`/design-page 되읽기`). 되돌릴 수 있는 것은 색 토큰·문구·글자 크기·아이콘이고, 나머지는 사람이 정한다.

**목표 품질은 Sonnet 수준의 낮은 모델로도 이상적인 결과물이 나오는 것이다.** 개발자와 PO 누구나 쓰기 때문이다.

이 목표가 `docs/system/` 문서의 작성 기준을 결정한다. 그 문서들의 1차 독자는 사람이 아니라 낮은 모델의 에이전트이며, 판단 기준은 `docs/system/README.md`의 「이 문서의 독자」에 있다.

## 이관 전 함께 정할 것

**공용 패키지를 어떤 형태로 전달할지.** 현재 `packages/*`는 모두 `private: true`이고 exports가 `.ts`/`.tsx` 소스를 직접 가리킨다. build 스크립트가 없다. 워크스페이스 안에서는 Next가 컴파일하지만, 블루키 저장소가 쓰려면 둘 중 하나를 골라야 한다.

- 소비자 쪽에서 `transpilePackages`로 소스를 그대로 컴파일한다. 우리 쪽 작업이 없고 소스맵이 그대로 남지만, 소비자 빌드 설정에 의존한다.
- 우리가 빌드 산출물을 만들어 넘긴다. 소비자 설정이 필요 없지만 빌드 파이프라인과 배포 방식을 정해야 한다.

Panda CSS 동시 사용 시 번들 용량 확인 결과와 함께 판단한다.

## 기술 스택 이슈

1차 컴포넌트는 shadcn + Tailwind, 블루키 기존 제품은 Next.js + Panda CSS를 사용한다. 선언 방식과 토큰 체계가 달라 동시 사용 시 번들 용량이 우려되며 개발 쪽에서 확인 후 공유한다.

디자인 토큰은 별도 변환 없이 그대로 사용한다. 컴포넌트를 교체하면 어차피 값이 바뀌고, 변환 과정에서 충돌 위험이 있기 때문이다.
