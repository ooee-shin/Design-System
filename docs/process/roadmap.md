# AX 전환 단계와 검증 계획

최종 목표는 요구사항에서 화면과 코드가 이어서 만들어지는 개발 환경이다. UI 시스템은 그 기반이며 목표 자체가 아니다.

## 5단계

| 단계 | 내용 | 1차 범위 |
| --- | --- | --- |
| 1 | 디자인 시스템(Figma) + UI 패키지 + 스토리북 + 디자인 토큰 구축 | 포함 |
| 2 | Figma MCP 연동 | 포함 |
| 3 | 스토리북 MCP 연동 | 포함 |
| 4 | 에이전트 설정·룰 | 제외 |
| 5 | 요구사항 → 화면 생성 → 코드 → 스토리 → PR/배포 자동화 | 제외 |

3단계까지는 안전하게 도달 가능하다고 보며, 이후는 테스트 소요 시간이 변수다.

## 부품을 참고하는 채널

기획자와 다른 개발자가 컴포넌트를 바로 참고할 수 있도록 스토리북을 표준화 목적으로 추가한다. `apps/studio`는 그 역할을 현재 수행하는 채널이자 스토리북 작업의 기반이며, 최종적으로는 스토리북이 표준 채널이 된다. Studio도 전달 범위에 포함한다.

`llms.txt`는 최우선 순위가 아니다. 다만 `docs/system/`을 단일 파일로 뽑아낼 수 있는 구조로 유지해 필요할 때 비용 없이 만들 수 있게 둔다.

## A/B 비교 검증

Figma에 들일 공수가 값어치를 하는지 판단하기 위한 품질 비교 테스트다.

| 안 | 방식 |
| --- | --- |
| A | Figma MCP를 경유해 코드 생성 |
| B | 컴포넌트만 주고 바로 코드 생성 |

**현재까지의 경험은 B안이 낫다.** Figma MCP를 물리면 오히려 디자인 시스템 코드를 잘 따르지 않았고, UI 키트만 보게 하는 쪽 결과가 좋았다.

**목표 품질은 Sonnet 수준의 낮은 모델로도 이상적인 결과물이 나오는 것이다.** 개발자와 PO 누구나 쓰기 때문이다.

이 목표가 `docs/system/` 문서의 작성 기준을 결정한다. 그 문서들의 1차 독자는 사람이 아니라 낮은 모델의 에이전트이며, 판단 기준은 `docs/system/README.md`의 「이 문서의 독자」에 있다.

## 이관 전 함께 정할 것

**공용 패키지를 어떤 형태로 전달할지.** 현재 `packages/*`는 모두 `private: true`이고 exports가 `.ts`/`.tsx` 소스를 직접 가리킨다. build 스크립트가 없다. 워크스페이스 안에서는 Next가 컴파일하지만, 블루키 저장소가 쓰려면 둘 중 하나를 골라야 한다.

- 소비자 쪽에서 `transpilePackages`로 소스를 그대로 컴파일한다. 우리 쪽 작업이 없고 소스맵이 그대로 남지만, 소비자 빌드 설정에 의존한다.
- 우리가 빌드 산출물을 만들어 넘긴다. 소비자 설정이 필요 없지만 빌드 파이프라인과 배포 방식을 정해야 한다.

Panda CSS 동시 사용 시 번들 용량 확인 결과와 함께 판단한다.

## 기술 스택 이슈

1차 컴포넌트는 shadcn + Tailwind, 블루키 기존 제품은 Next.js + Panda CSS를 사용한다. 선언 방식과 토큰 체계가 달라 동시 사용 시 번들 용량이 우려되며 개발 쪽에서 확인 후 공유한다.

디자인 토큰은 별도 변환 없이 그대로 사용한다. 컴포넌트를 교체하면 어차피 값이 바뀌고, 변환 과정에서 충돌 위험이 있기 때문이다.
