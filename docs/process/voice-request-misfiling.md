# 점주의소리 · 지원요청 오입 개선 화면

`2026-09-17`에 받은 기획을 `/screens/admin`과 `/screens/sto`에 구현하는 작업이다. 이어서 진행할 제품 화면 작업 세 건 가운데 첫 번째이며, 나머지 두 건은 아직 이름과 범위를 받지 않았다.

## 무엇을 해결하는 화면인가

실무 요청이 점주의소리로, 제안이 지원요청으로 잘못 접수되고 있다. 잘못 들어온 건을 반대 채널로 옮길 수단이 없어서 담당자가 점주의소리 답변으로 종결하거나 실무진이 지원요청에 다시 등록하는 우회 처리를 하고 있으며, 그 결과 점주의소리 데이터에 실무 건이 섞여 통계를 믿을 수 없게 되었다.

기획이 세운 목표는 셋이다. 접수 단계에서 점주가 종류를 직접 고르게 해서 오입을 줄이고, 그래도 들어온 오입 건은 정식 전환 기능으로 옮기며, 기존 상태값과 답변 로직과 메뉴 구조는 그대로 유지한다.

## 입력 자료

기획안과 프로토타입은 사용자가 Claude 아티팩트로 갖고 있다. 저장소에는 두지 않으며, 필요하면 사용자에게 링크를 요청한다.

- 기획안 `점주의소리 · 지원요청 오입 개선 상세 기획 (v2)`. 화면에 들어갈 문구와 조건이 확정되어 있으므로 여기에 없는 문구를 새로 지어내지 않는다.
- 프로토타입 `점주의소리 · 지원요청 오입 개선 프로토타입`. 동작과 분기를 확인하는 자료다.

**프로토타입의 화면 틀은 참고 대상이 아니다.** 지금 코드로 참고할 수 없는 이전 버전 서비스의 레이아웃을 따라 그린 것이기 때문이다. 화면은 `AdminLayout`과 App Layout 위에 다시 짠다.

## 만들 화면

`apps/studio/src/components/screens/screen-registry.ts`에 다섯 줄이 선다. 각 줄이 목록과 상세를 함께 갖는다.

| 루트 | 이름 | 범위 |
| --- | --- | --- |
| admin | 점주의 소리 | 목록·상세, 지원요청으로 전환, 답변 시 전환 잠금 |
| admin | 지원요청 | 목록·상세, 점주의소리로 전환, 채팅 |
| sto | 점주의 소리 | 목록·상세, 전환된 건 표시 |
| sto | 지원요청 | 목록·상세 탭(요청 내용·채팅) |
| sto | 통합 작성 폼 | 종류 선택·카테고리·제목·내용·첨부, 불일치 안내와 확인 시트, 접수 완료 |

## 화면마다 보여 줄 상태

Studio 화면은 눈으로 확인하려고 만드는 자리이므로 실제로 동작할 필요는 없지만, 겉모습이 갈라지는 경우는 화면 위에서 골라 볼 수 있어야 한다. 하나만 그리면 나머지를 확인할 방법이 없기 때문이다.

**관리자 점주의 소리 상세**

| 상태 | 화면 |
| --- | --- |
| 보통 | 전환 버튼이 눌린다 |
| 답변 등록됨 | 회색 안내가 서고 전환이 잠기며 파생 등록만 남는다 |
| 전환됨 | 주황 안내가 서고 답변·처리상태·담당자가 모두 잠긴다 |

**관리자 지원요청 상세**

| 상태 | 화면 |
| --- | --- |
| 보통 | 전환 버튼이 눌린다 |
| 전환으로 생성된 건 | 상단 안내가 서고 등록자가 이관자로, 원 작성자가 별도 행으로 표시된다 |
| 전환 완료 건 | 완료 처리되어 채팅이 잠기고 완료보고에 전환이 기록되어 있다 |

**사장님 앱 점주의 소리 상세**는 보통과 전환된 건 둘이고, **통합 작성 폼**은 종류 미선택과 진입 메뉴 일치와 진입 메뉴 불일치 셋이다.

## 새로 만들 컴포넌트

`apps/studio/src/components/candidates/`에 셋을 더한다. 화면 안에서 먼저 쓰고 두 번째 화면에서 다시 검증한 뒤에 공용 자산으로 올릴지 판단한다. 제작 철학은 [README.md](README.md)의 「Template First, Asset Later」를 따른다.

| 컴포넌트 | 쓰는 자리 |
| --- | --- |
| Table | 관리자 목록 두 개. 열 정의, 행 클릭, 전환된 건을 흐리게 두는 처리 |
| Dialog | 전환 팝업 두 종, 답변 등록, 처리상태 변경 |
| Sheet | 사장님 앱에서 진입 메뉴와 다른 종류를 골랐을 때 등록 직전의 확인 |

## 차례

**1단계는 점주의 소리로 네 축을 세운다.** 관리자 목록, 관리자 상세, 앱 목록, 앱 상세를 만들며 Table과 Dialog가 여기서 정해진다. 이 뼈대가 어긋난 채로 넘어가면 뒤의 여덟 화면을 모두 고쳐야 하므로, **화면을 하나 만들 때마다 사용자에게 보이고 확인을 받은 뒤 다음으로 넘어간다.**

**2단계는 같은 네 축을 지원요청으로 넓힌다.** 1단계의 뼈대에 내용을 채우는 일이라 새로 판단할 것이 거의 없으므로 **네 화면을 모두 만들어 한 번에 보인다.** 이 단계에서 1단계의 뼈대가 실제로 재사용되는지 드러난다. 앱 상세에만 요청 내용과 채팅 탭 구조가 더해진다.

**3단계는 통합 작성 폼과 접수 완료를 만든다.** 두 채널의 카테고리 체계를 모두 알아야 하는 화면이라 마지막에 둔다. Sheet를 여기서 만들며, 폼을 먼저 보인 뒤 접수 완료를 이어 만든다.

## 기획에서 확인이 필요한 것

**답변 등록 버튼의 라벨이 길다.** 기획은 「점주의소리에서 처리하기로 확정하고 답변 등록」을 쓰도록 적고 있으나 이것은 문장이라 버튼 안에서 두 줄로 접힌다. 경고 문구가 모달 상단에 이미 있으므로 라벨을 짧게 두는 편이 나을 수 있다. 1단계에서 실제로 그린 뒤 폭을 재서 사용자에게 보고한다.
