# 블루키 리뉴얼

`/renewal/*` 는 블루키 제품 화면을 한 건씩 구현하는 작업장이다. `2026-09-22` 에 Studio 의 `/screens` 에서 sandbox 로 옮겼다. 화면은 `src/app/(renewal)/renewal/` 아래, 부품은 이 폴더(`screen-chrome` · `screen-registry` · `screen-work-list` · `screen-root-tabs`)와 `src/components/candidates/` 에 있다.

`/generate-code` 가 만든 화면(`src/screens.ts` 에 등록된 것)과는 다른 자리다. route group `(renewal)` 로 두어 sandbox 의 화면 규칙 검사가 이 화면들을 생성 화면으로 세지 않는다. 까닭은 `src/app/(renewal)/layout.tsx` 에 있다.

## 규칙

제품 화면 자체를 구현하는 자리이므로 문서형 레이아웃을 따르지 않고 각자의 레이아웃 규칙을 갖는다. 관리자는 뷰포트를 전부 쓰고, 앱 화면은 웹에서 접근했을 때 모바일 뷰가 화면 가운데에 선다.

- 두 앱 화면은 공용 `MobileWebView`를 함께 쓴다. 화면마다 폭을 직접 적으면 한쪽만 고쳤을 때 두 화면의 기준이 갈린다.
- **모바일 뷰는 기기 모형이 아니다.** 둥근 모서리와 그림자로 상자를 만들지 않고 높이도 고정하지 않는다. 웹에서 앱에 접근한 실제 페이지이므로 창 높이를 그대로 쓰고, 넓은 화면에서 좌우 바닥과 만나는 자리만 한 줄로 구분한다.
- **넓은 화면에서 좌우를 어떻게 확장할지는 정하지 않았다.** 가능성만 열어 두었으므로 그 자리를 임의로 채우지 않는다.
- 돌아가는 링크를 화면 위에 고정하지 않는다. 그 링크가 실제 화면 요소를 가려 무엇을 보고 있는지 확인하는 일을 방해하며, 이는 관리자 화면과 앱 화면이 다르지 않다. 돌아가는 길은 브라우저 뒤로 가기가 갖는다.
- **각 루트의 첫 화면은 완성된 앱이 아니라 작업 목록이다.** 이 아래는 기능 화면을 한 건씩 만드는 자리이고 화면끼리 이어지는 데모가 아니다. 무엇을 만들 예정이고 어디까지 왔는지를 먼저 보여 주지 않으면 열어 본 사람이 덜 만들어진 화면을 고장난 것으로 읽는다.
- **화면은 눈으로 확인하려고 만든다.** 화면에 보이는 요소가 실제로 동작하지 않을 수 있다. 목록의 첫 화면이 이 사실을 먼저 알린다.

`src/components/candidates/` 는 아직 `@ooee/ui` 에 없는 후보 부품이다. `tabs` 는 Studio 의 프레젠테이션 목록도 써서 Studio 에 같은 파일이 한 벌 더 있다 — 한쪽을 고치면 다른 쪽도 본다. `@ooee/ui` 로 올라가면 둘 다 그쪽을 쓴다.
