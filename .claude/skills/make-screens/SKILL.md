# /make-screens

**하는 일은 하나다.** 요청을 화면 몇 장으로 나누고, 그 화면을 만들고, 무엇을 만들었는지 한 장에 적는다.

## 하지 않는 것

가지 만들기, `git commit`·`push`, pull request, 머지, 배포 확인, 결과 댓글, 이슈 닫기. **모두 러너가 한다.** 그 명령들은 이 명령에 열려 있지도 않다.

기다리는 일과 되풀이되는 일은 스크립트의 몫이다 — 까닭은 `scripts/harness/plan.mjs` 머리말.

## 순서

### 1. 이슈를 읽는다

```bash
node scripts/harness/issue.mjs <n>
```

출력의 `mode`·`generateArgs`·`fix`·`project`·`viewports`·`notes`·`fields` 를 쓴다. 본문을 눈으로 다시 나누지 않는다. **`problems` 가 있으면 러너가 이미 막았으므로 여기까지 오지 않는다.**

- **`project.undecided` 가 `true` 면 프로젝트를 이 명령이 정한다.** 묻지 않는다(`2026-09-23` 개발자).
  1. `apps/sandbox/src/screens.ts` 의 `SANDBOX_PROJECTS` 와 그 프로젝트에 든 화면 이름을 읽는다.
  2. 요구사항이 부르는 제품·사용자·흐름이 있는 프로젝트의 것과 같으면 **그 프로젝트**다. 「하네스 시험」은 하네스를 시험하는 자리라 요구사항이 시험이라고 하지 않으면 넣지 않는다.
  3. 맞는 곳이 없으면 **새 프로젝트**다. 이름은 요구사항이 부르는 제품·업무 이름이고(두 어절에서 네 어절), 사람 이름·「테스트」·날짜는 쓰지 않는다. id 는 소문자, 공백은 붙임표, 그 밖의 기호는 뺀다.
  4. 정한 것을 `needsDecision` 첫 줄에 「프로젝트를 정했다: 「<이름>」(있는 것 | 새로 만듦) — <까닭 한 줄>」로 남긴다.
- **`mode` 가 `수정` 이면 있는 화면을 제자리에서 고친다.** `fix.target` 이 그 화면을 만든 요청이다. 그 요청의 머지된 pull request 를 `gh pr list --state all --base dev --search '"요청: #<fix.target>" in:body'` 로 찾아 본문 `## 화면별 인수` 에서 key 와 앞 인수 원문을 읽는다. 화면 코드는 열지 않는다. 그 key 가 `screens.ts` 에 없으면 멈춘다. 화면은 그 하나이고 2단계를 건너뛴다.
- `fields.similar`·`fields.onSubmit` 이 비어 있지 않으면 `needsDecision` 에 「반영하지 않은 칸 <라벨>: <값>」으로 남긴다.

### 1-1. 인수에 「개선」이 있으면 다시 만드는 회차다

러너가 `/make-screens <n> 개선 러너` 로 부른다. 기획자가 결과 카드에서 😕 를 누르고 까닭을 적은 것이다.

```bash
node scripts/harness/decision.mjs <n>      # reason 이 그 까닭이다
```

1. **사유가 앞 회차의 어느 항목을 가리키는지 본다.** 그 회차 pull request 본문(`gh pr view <번호> --json body`)의 「판단이 필요한 것」·「화면별 인수」와 대조한다. 번호는 결과 댓글 작업 줄의 `PR #<번호>` 다.
   - 가리키는 항목이 있으면 개선이다. 지어낸 것을 고쳐 달라는 사유도 개선이다 — 요청이 비워 둔 자리를 기획자가 채우는 일이다.
   - **어느 항목도 가리키지 않는 새 요구면** 그것이 이 화면에 더하는 것인지 본다. 더하는 것이면 **만든다** — 기획자가 화면을 보고 떠올린 것이라 이 화면의 일이다. `needsDecision` 첫 줄에 「요청에 없던 것을 개선으로 받았습니다: <사유>」를 적어 원본이 어디서 늘었는지 남긴다. 이 화면의 일이 아니면(다른 화면·다른 프로젝트) 그때만 「## 묻고 멈춤」으로 어느 화면의 일인지 적고 멈춘다.
2. **사유가 가리키는 화면만 다시 만든다.** 인수는 그 화면의 앞 회차 인수 원문 뒤에 ` 개선: <사유 원문>` 을 붙인 것이다. 본문에 인수가 없으면 멈춘다. 인수를 찾으려고 `page.tsx` 를 열지 않는다.
3. **앞 회차 코드를 읽지 않는다.** generate-code 가 같은 대화에서 도는데, 여기서 읽은 코드가 맥락에 남아 그 명령의 「다른 화면의 코드 읽기」 금지를 우회한다.
4. `plan.json` 의 `screens` 에는 **이 요청의 화면을 모두** 넣고, 다시 만들지 않은 화면에는 `"remade": false` 를 적는다. 결과 댓글의 표에는 모두 나오고 「추가한 페이지」에는 다시 만든 것만 들어간다.
5. `other` 첫 줄을 「<앞 회차>회차 개선 반영: <사유 한 줄>」로 적는다.

### 2. 만들 화면을 정한다

요구사항이 여러 화면을 부르면 나눈다(「2-3페이지」·「자율 4-5페이지」·흐름을 이루는 화면들). 한 장이면 이 단계를 건너뛴다.

- **확인받지 않고 정한다.** 물을 사람이 없다. 나눈 목록을 `needsDecision` 첫 줄에 「확인받지 않고 나눈 화면: <key>·<key>…」로 남기면 기획자가 결과 카드에서 보고 개선이나 반려로 고친다.
- 화면마다 정할 것은 **이름**, **요청 원문에서 온 것**, **지어낸 것**(화면에 보일 항목·버튼 문구·기본값 가운데 요청에 없는 것) 셋이다.
- 화면끼리 링크로 이을 때는 **이 회차에 함께 만드는 화면만** 가리킨다. 만들지 않을 화면 주소를 걸면 열리지 않는 링크가 남는다.

### 3. 화면마다 generate-code 를 돌린다

`/ooee-harness:generate-code` 를 화면마다 한 번씩 부른다. 인수는 이 꼴이다.

```
<화면 이름>. <요청 원문에서 온 것> 지어냄: <지어낸 것> 프로젝트: <id> 유형: <web, tablet, mobile 가운데 고른 것들>
```

- 새 프로젝트면 `새 프로젝트 이름: <이름>` 을 뒤에 붙인다.
- 수정 요청이면 **앞 인수 원문 + ` 수정: <fix.instruction>` + ` 고칠 화면: <key>`** 다.
- 개선 회차면 앞 회차 인수 뒤에 ` 개선: <사유 원문>` 을 붙인다.
- 한 장 요청이면 `issue.mjs` 의 `generateArgs` 를 그대로 쓴다(`프로젝트: <정한다>` 는 1단계에서 정한 id 로 바꾼다).

**하위 명령의 보고는 이 명령의 끝이 아니다.** generate-code 가 「pull request 준비 완료」를 내면 그 화면 하나가 끝난 것이다. 남은 화면이 있으면 이어 가고, 없으면 4단계로 간다(`2026-09-24` #85 가 여기서 끝냈다).

- generate-code 보고의 「판단이 필요한 것」·「미확정 자산 후보」 줄은 화면 이름을 앞에 붙여 `needsDecision` 에, 「막힌 명령」(없음이 아니면)은 `other` 에 옮긴다. 러너는 이 보고를 읽지 않고 `plan.json` 만 읽으므로, 옮기지 않으면 pull request 본문과 결과 댓글에서 사라진다. `issue.mjs` 의 `notes` 가운데 파싱 주의(라벨이 줄 처음이 아님·라벨 없는 앞 글)도 `other` 에 옮긴다 — 프로젝트 선택은 1단계가 이미 `needsDecision` 에 옮긴다.

### 4. sandbox 에서 띄워 보고 잰다

```bash
pnpm --filter @ooee/sandbox build
node scripts/visual/inspect.mjs --serve apps/sandbox/out --path "/<key>?frame=1" --viewport <WxH> --shot <key>-<유형>
```

- 뷰포트는 화면 유형이 정한다 — 웹 `1440x900`, 태블릿 `1024x768`, 모바일 `390x844`. **유형이 여럿이면 폭마다 한 번씩** 찍는다.
- 기계로 재는 둘: `h1` 이 있는지, 가로 넘침이 없는지(`documentElement.scrollWidth` 가 뷰포트 폭 이하).
- 화면은 「보기 폭」 액자(iframe) 안에 열리므로 검사는 `?frame=1` 로 액자 안 문서를 직접 연다 — 액자 밖 문서에는 `h1` 이 없다.
- 찍은 그림을 **눈으로 본다.** 겹침·잘림·빈 화면이 있으면 고치고 다시 잰다. 고친 것은 `other` 에, 고치지 않고 남긴 판단은 `needsDecision` 에 적는다.
- 화면 위의 「보기 폭」 전환은 sandbox 가 얹는 것이라 화면 코드가 신경 쓰지 않는다.

### 5. 무엇을 만들었는지 적고 멈춘다

`.harness-work/issue-<n>/plan.json` 에 `Write` 로 쓴다. **이 파일이 이 명령의 결과물이다.**

```json
{
  "issue": 85,
  "screens": [
    {
      "key": "invoice-dashboard",
      "name": "자동 송장 대시보드",
      "project": "자동-송장-api",
      "viewports": ["web"],
      "args": "3단계에서 generate-code 에 넘긴 인수 원문 그대로"
    }
  ],
  "componentsAdded": [],
  "componentsUsed": ["Badge", "Button"],
  "other": ["모바일에서 표가 잘려 카드형 목록으로 바꿨다"],
  "needsDecision": ["예시 데이터 셋은 요청에 없어 정했다"]
}
```

| 칸 | 무엇 |
| --- | --- |
| `screens[].key` | `screens.ts` 에 등록된 key. 소문자·숫자·붙임표 |
| `screens[].name` | `screens.ts` 에 등록된 이름. 결과 댓글의 표와 「추가한 페이지」가 이 글자다. 이름·프로젝트·폭이 등록과 다르면 러너가 등록값으로 덮어쓰고, 등록에 없는 key 면 멈춘다 |
| `screens[].project` | 그 화면이 든 프로젝트 id |
| `screens[].viewports` | `web`·`tablet`·`mobile` 가운데 고른 것들 |
| `screens[].args` | 3단계에서 실제로 넘긴 인수 원문. pull request 본문에 그대로 실려 다음 회차가 읽는다 |
| `componentsAdded` | `@ooee/ui` 에 새로 더한 컴포넌트. 보통 비어 있다 |
| `componentsUsed` | 쓴 컴포넌트 이름. 겹치지 않게 |
| `other` | 그 밖에 한 일. 개선 회차면 「<앞 회차>회차 개선 반영: <사유 한 줄>」 |
| `screens[].remade` | 개선 회차에서 다시 만들지 않은 화면에만 `false`. 없으면 다시 만든 것으로 본다 |
| `needsDecision` | 요청에 없어 정한 것, 확인받지 않고 나눈 목록, 반영하지 않은 칸, generate-code 가 낸 판단 항목(「판단이 필요한 것」·「미확정 자산 후보」) 포함. 화면이 여럿이면 이름을 앞에 붙인다 |

쓴 뒤 **보고의 첫 제목을 「## 화면을 만들었다」로 하고 멈춘다.** 화면 표(이름·key·폭)와 `needsDecision` 을 함께 적는다. 러너가 이 파일을 다시 확인하고 pull request 부터 결과 댓글까지 한다.

### 뜻이 갈리면 묻지 말고 **만들어서 보여 준다**

`2026-09-24` 개발자: 「그냥 이렇게 하면 어때요? 라고 제안해서 우리가 오케이 하면 그대로 올리면 되잖아. 왜 실패로 돌리려는 거야」.

요구사항이 여러 뜻으로 읽힐 때 **묻고 멈추지 않는다.** 가장 그럴듯한 하나를 골라 만들고, **무엇으로 읽었는지와 버린 갈래를** `needsDecision` 첫 줄에 적는다. 기획자는 글로 된 물음이 아니라 **실제로 도는 화면**을 보고 👍 👎 😕 로 답한다. 그것이 이 하네스가 카드에 버튼을 둔 까닭이다.

```
needsDecision[0]: 「상단 검색 UI 개선」을 「지난 대화를 검색하는 입력창을 머리말 아래에 새로 둔다」로 읽었습니다.
                  달리 읽을 수 있었던 것: 질문 입력줄을 위로 옮긴다 · 다른 화면의 검색을 말한다.
                  다르면 😕 개선으로 알려 주세요.
```

- **고르는 기준**은 「요청자가 이 화면에서 무엇을 하고 싶은가」다. 화면에 없는 것을 말하면 **새로 두라는 뜻**으로 읽는다(「개선」이라고 적혀 있어도 그렇다 — 기획자는 화면 구조를 외우고 있지 않다).
- 지어낸 것이 커도 만든다. **되돌리는 비용보다 못 보는 비용이 크다** — 화면은 sandbox 에만 있고, 개선·반려 버튼이 한 번에 되돌린다.
- 요구가 여러 화면에 걸리면 이 요청이 가리키는 화면 하나에만 넣고 나머지는 `needsDecision` 에 적는다.

**그래도 만들 수 없을 때만 멈춘다.** 고칠 화면을 찾지 못함, 요구사항이 비어 있음, 검사가 화면 자리 밖에서 실패, 도구가 막힘 — 무엇을 만들지 고를 수조차 없는 자리다.

**멈출 때는 `plan.json` 을 쓰지 않고 멈춘 자리와 까닭을 적는다.** 러너가 그 제목과 줄을 결과 채널 카드로 옮기므로, 제목이 기획자가 받는 말이 된다. 둘을 가린다.

| 첫 제목 | 언제 | 카드 |
| --- | --- | --- |
| `## 묻고 멈춤` | **요청자가 답해야 풀린다** — 무엇을 만들지 요청에 없다, 고칠 대상이 화면에 없다, 사유가 가리키는 것이 없다 | 🙋 「폼으로 다시 내 주세요」 |
| `## 처리 중 실패` | **개발자가 봐야 풀린다** — 검사가 화면 자리 밖에서 실패, 도구가 막힘, 하네스가 고장 | ⚠️ 「개발자에게 알려 주세요」 |

묻고 멈출 때는 **고를 수 있는 갈래를 번호로 적는다.** 기획자가 그 가운데 하나를 골라 한 줄로 적으면 다음 요청이 된다. 갈래 없이 「알 수 없다」만 적으면 기획자는 무엇을 적어야 할지 모른다(`2026-09-24` #99).

**갈래를 적을 수 있다면 대개 만들 수 있다.** 위 「뜻이 갈리면 만들어서 보여 준다」로 간다. 묻는 것은 갈래조차 세울 수 없을 때다.

## 러너에서 돌 때

인수 끝의 `러너` 는 이 Mac 의 1분 감시가 부른 것이다. 대화할 사람이 없으므로 묻지 않고 정하며, 정한 것은 모두 `needsDecision` 에 남긴다. 기획자는 결과 카드에서 보고 개선·반려로 고친다.

- **기다리지 않는다.** 이 차례가 끝나면 세션도 끝나 나중에 올 알림을 받을 수 없다. 오래 걸리는 명령을 배경으로 밀어 두고 기다리는 도구를 부르지 않는다.
- **한 줄에 명령을 여러 개 묶지 않는다**(`A && B`·`for … done`). 권한 검사가 그 줄 전체를 모르는 명령으로 보아 거부한다.
- 막힌 명령은 형태를 바꿔 다시 시도하지 않고 보고에 적는다.
